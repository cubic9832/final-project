# 설계 및 공통화 기준

React·Spring·Python의 구현과 리팩터링에서 SOLID를 지향한다. 현재 기능의 책임과 변경 이유를 기준으로 구조를 정하며, 원칙을 적용하기 위해 불필요한 클래스·인터페이스·계층을 만들지 않는다.

## SOLID 적용

| 원칙 | 적용 기준 |
| --- | --- |
| 단일 책임 (SRP) | 컴포넌트·함수·클래스·모듈은 응집된 책임을 갖는다. UI 표현, 비즈니스 판단, 외부 입출력처럼 변경 이유가 다른 책임을 분리한다. |
| 개방·폐쇄 (OCP) | 실제 변형 요구가 생기면 조합·전략·주입으로 확장 지점을 마련한다. 미래의 가능성만으로 확장 구조를 만들지 않는다. |
| 리스코프 치환 (LSP) | 대체 구현은 호출자가 기대하는 입력·출력·오류·동작 계약을 유지한다. 상속으로 계약을 지키기 어렵다면 조합을 사용한다. |
| 인터페이스 분리 (ISP) | 소비자가 사용하는 기능만 노출한다. 관련 없는 메서드나 props를 강제로 제공하게 하는 거대한 인터페이스를 피한다. |
| 의존성 역전 (DIP) | 핵심 정책을 HTTP·DB·파일·모델 실행 같은 외부 구현과 분리한다. 교체가 필요한 경계에 작은 계약을 두고 의존성을 주입한다. 모든 구현에 일대일 인터페이스를 만들지는 않는다. |

## 컴포넌트·함수·모듈로 분리하는 기준

- 별도의 책임과 변경 이유가 있거나, 독립적인 상태·동작·입출력 계약을 설명할 수 있으면 분리를 검토한다. 한 곳에서만 사용하더라도 이 기준에 해당하면 분리할 수 있다.
- 같은 의미의 UI·로직이 반복되고 같은 이유로 함께 변경되어야 한다면 추출한다. 줄 수나 사용 횟수만으로 기계적으로 분리하지 않는다.
- 분리한 요소의 이름·입력·출력이 역할을 명확하게 표현하고, 호출자가 내부 구현을 알 필요가 없어야 한다.
- 단순 마크업이나 짧은 코드를 감싸는 것 외에 책임·재사용·가독성 개선이 없다면 현재 위치에 둔다.

## 공통 기능으로 승격하는 기준

- 먼저 해당 기능 내부에서 관리한다. 서로 다른 기능에서 실제로 사용하는 동일한 의미·계약의 요소만 공통 영역으로 이동한다.
- 모양이나 코드가 비슷해도 도메인 규칙·변경 이유가 다르면 별도로 유지한다. 도메인별 정책을 범용 유틸리티에 숨기지 않는다.
- 공통 요소는 특정 기능의 내부 구현을 import하지 않는다. 필요한 값이나 동작은 명시적인 입력·콜백·작은 계약으로 전달한다.
- 호출 기능을 구분하는 플래그와 조건 분기가 계속 늘어나면 공통화 범위를 줄이거나 기능별 구현으로 나눈다.
- 예상 재사용을 위해 빈 공통 모듈을 만들거나 처음부터 범용 프레임워크를 구축하지 않는다. 명명과 배치는 [기능별 기준](naming.md)을 따른다.

## 기술별 적용

| 구분 | 분리 기준 |
| --- | --- |
| React | 독립된 UI 의미·상태·상호작용은 컴포넌트로 분리한다. 재사용하는 상태·Effect 로직은 custom Hook, React에 의존하지 않는 계산·변환은 일반 함수로 둔다. Hook 호출 제약 등 프레임워크 규칙도 함께 따른다. |
| Spring | Controller는 HTTP 입출력, Service·도메인은 비즈니스 규칙, Repository는 영속성 접근을 담당한다. 여러 기능에서 같은 의미로 사용하는 정책·외부 연동만 공통화하며 범용 Service에 관련 없는 기능을 모으지 않는다. |
| Python 딥러닝 | 데이터 읽기·전처리·모델 정의·학습·평가·추론의 변경 이유에 따라 분리한다. 학습과 추론에서 동일해야 하는 전처리는 같은 구현을 사용한다. 순수 변환과 파일·모델 실행 등 입출력 경계를 구분한다. |

## 변경 검증

- 추출·공통화 후에도 기존 사용자 동작과 비즈니스 계약을 유지한다.
- 검증은 [테스트 기준](testing.md)에 따라 핵심 로직과 주요 사용자 흐름에 집중한다. 파일 분리나 인터페이스 추가 자체를 검증하는 허수 테스트를 만들지 않는다.
